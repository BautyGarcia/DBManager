# Platform reference (for agents and operators)

Read this before doing anything on a dbm host that is not "provision a Next.js app" (the `/dbmanager` skill covers that). It explains what is running, how traffic and data flow, what is safe to touch, and how to reason about a new kind of request. It never contains secrets or instance-specific values; section 1 shows how to read those.

## 1. Find out where you are

Run these first, from the operator's machine. They are read-only.

```bash
dbm --version                 # CLI present? (built from the db-manager checkout; `npm run build` after pulling)
dbm list                      # every project: status, memory, disk, storage, last backup
dbm doctor                    # health of the whole platform; exit 2 means something is wrong
python3 -c 'import json,os;c=json.load(open(os.path.expanduser("~/.dbm/config.json")));print({k:c[k] for k in ("sshHost","domain","dbHost","s3Host","webDomain","dokployUrl","tls")})'
```

`~/.dbm/config.json` also holds API keys and tokens: print only the fields above. `~/.dbm/state.json` holds every project's passwords: never print it.

SSH: `ssh root@<sshHost>` with the operator's key (key-only, passwords are disabled). The Dokploy dashboard is `dokployUrl` and only opens over Tailscale.

## 2. Topology

One Ubuntu 24.04 VPS runs everything. Apps do not run on it: they run on Vercel and connect over the internet.

```
Vercel functions ──TLS──► db.<domain>:6432 ──► dbm-pgbouncer ──► pg-<slug>-<rand>:5432   (one Postgres container per project)
browser / Vercel ─HTTPS─► s3.<domain>      ──► Traefik ──► dbm-garage:3900                (S3 API)
browser ─────────HTTPS─► <slug>.web.<domain> ► Traefik ──► dbm-garage:3902                (public buckets only)
operator (tailnet) ─────► <host>.ts.net:8443 ► Dokploy dashboard / API
nightly ────────────────► Backblaze B2: dbm-dumps (pg_dump per project), dbm-storage (mirror of every bucket)
```

Orchestration is Dokploy on Docker Swarm. Traefik (managed by Dokploy) terminates TLS with Let's Encrypt for everything public.

## 3. What runs where

| Component | Container / service | Image (pinned in `src/core/compose.ts`) | Role |
|---|---|---|---|
| Dokploy | `dokploy` service + `dokploy-postgres` | `dokploy/dokploy`, `postgres:16` | Orchestrator, dashboard, backup scheduler. Its own Postgres is internal to Dokploy, not a project database |
| Traefik | `dokploy-traefik` | `traefik:v3` | Ports 80/443, TLS, routing |
| Project databases | `pg-<slug>-<6 chars>` Swarm services | `postgres:18` (or 17) | One per project, 512 MB memory cap by default (`dbm create --memory`) |
| PgBouncer | `dbm-pgbouncer` | `edoburu/pgbouncer` | Single public entry to all databases on 6432, TLS verify-full |
| Garage | `dbm-garage` | `dxflrs/garage` | S3 storage, single node, replication factor 1. S3 API 3900, web 3902, admin 3903 (localhost only) |
| Certs dumper | `dbm-certs-dumper` | `ldez/traefik-certs-dumper` | Copies Traefik's certificate for `db.<domain>` to PgBouncer |

Host directories owned by dbm (all under `/etc/dokploy/dbm/`): `pgbouncer/` (ini + userlist, regenerated by `dbm`), `certs/`, `garage/` (garage.toml), `rclone/` (B2 + Garage read-only credentials). Traefik routes written by dbm live in `/etc/dokploy/traefik/dynamic/dbm-*.yml`.

## 4. Network and firewall

- **Public inbound:** 80/tcp, 443/tcp and udp, 6432/tcp, 22/tcp (SSH, key-only), 41641/udp (Tailscale). Nothing else.
- Docker publishes ports before ufw sees them, so dbm adds a `DOCKER-USER` chain (in `/etc/ufw/after.rules`) that drops any new inbound connection to a published container port except 80, 443 and 6432. Dokploy's port 3000 listens on 0.0.0.0 but is blocked this way; it is reachable only through Tailscale.
- **Tailscale** carries the dashboard and Dokploy API (`tailscale serve` on 8443). If Tailscale is down, apps keep working; only administration stops.
- **Internal network:** `dokploy-network` (Swarm overlay). Every project Postgres, PgBouncer, Garage, Traefik and any app deployed through Dokploy sit on it and can reach each other by service name. Isolation between projects is by credentials (each project has its own roles), not by network.
- Hardening: sshd key-only, fail2ban, unattended-upgrades, Docker log rotation. `dbm init` sets all of it; do not hand-edit ufw or iptables without reading `src/core/harden.ts`.

## 5. DNS and routing

Three A records point at the VPS: `db.<domain>`, `s3.<domain>`, `*.web.<domain>`.

- `db.` is only used for the TLS certificate and the PgBouncer hostname.
- `s3.` is the S3 API (Traefik file provider, `dbm-s3.yml`).
- `*.web.` is **reserved for public buckets**: `<slug>.web.<domain>` maps to Garage's web endpoint (`dbm-web-<slug>.yml`, written by `dbm storage public`). Do not route anything else under `*.web.`.
- Anything new that needs a hostname (a demo backend, a tool) needs its **own A record**, for example `demo-x.<domain>`, and a Dokploy domain or a Traefik route. Traefik gets the certificate automatically once DNS points here.

## 6. Data plane

**Postgres.** Each project has a database `<slug_db>` owned by `<slug_db>_app` (no superuser, used by the app) and an admin role `<slug_db>_admin` (used by dbm). Apps get two URLs from `dbm env <slug>`:

- `DATABASE_URL`: PgBouncer transaction mode, database `<slug>`. For the app at runtime. No session features (prepared statements across transactions, `LISTEN`, advisory locks held across statements).
- `DATABASE_URL_SESSION`: PgBouncer session mode, database `<slug>_session`, pool of 3. For migrations (`drizzle-kit`) and anything needing a real session.

Both require TLS with full verification (`sslmode=verify-full`, or postgres.js `ssl: 'verify-full'`). PgBouncer reloads its certificate nightly at 04:10 (server time).

**Storage.** One Garage bucket per project, named `<slug>`, with its own access key. Private by default; browsers upload and download through presigned URLs. `dbm storage public <slug>` makes the whole bucket public at `https://<slug>.web.<domain>` (visibility is per bucket, not per prefix). Supabase imports land under `<bucket>/` prefixes inside that one bucket.

**Auth.** better-auth runs inside each app, with its tables in the project database. There is no central auth service.

## 7. Backups and recovery

| What | When (UTC) | Where | Retention |
|---|---|---|---|
| `pg_dump -Fc \| gzip` per project, scheduled by Dokploy | 06:00 to 06:24, minute derived from the slug | B2 `dbm-dumps/<appName>/db/<slug>/<ISO time>.sql.gz` | 30 days (bucket lifecycle) |
| Mirror of every Garage bucket (`rclone sync --size-only --max-delete 50`) | 06:30 (`/etc/cron.d/dbm-storage-sync`) | B2 `dbm-storage/storage/<slug>/` | Deleted objects kept 30 days as hidden versions |
| Garage metadata snapshots | after the mirror | B2 `dbm-storage/garage-meta/` | same |

Tools: `dbm backup <slug>` (dump now and list dumps), `dbm restore <slug> <id|latest>` (in place, asks to confirm) or `--as <slug>` (into a new project). `docs/runbook.md` covers in-place restore, a destroyed project, a lost VPS, storage recovery, and the Backblaze daily-cap failure mode (403 on HEAD or download).

Redis, app containers and anything else not created by `dbm` are **not backed up**.

## 8. The operator's machine

- `~/.dbm/config.json`: host, domain, Dokploy URL and API key, Garage admin token, B2 destination id.
- `~/.dbm/state.json`: every project (Dokploy ids, roles, passwords, bucket keys) and tombstones of destroyed projects. Rotated backups sit next to it as `state.json.bak.*`. Losing this file means losing the passwords, though databases and buckets survive on the VPS.
- `~/.dbm/lock`: a PID lock; one `dbm` command at a time.
- `~/.claude/skills/dbmanager`: symlink to `skills/dbmanager/` in the checkout.

## 9. Capacity

Fixed platform cost is about 1.5 GB of RAM (Dokploy alone is roughly 1 GB). An idle project Postgres uses about 30 MB; a busy one up to its 512 MB cap, plus page cache outside the container. Check headroom with `dbm list` and `ssh root@<host> free -m` before adding anything heavy. There is no swap.

## 10. Rules

- Never print or commit secrets: `.env.local`, `state.json`, `config.json` values, `dbm create`/`dbm env` output, rclone configs.
- `dbm destroy`, `dbm restore` into a live project and `dbm init` are the operator's decisions. Ask first.
- Change platform services through `dbm` or Dokploy, never with `docker service rm/update` or by editing files under `/etc/dokploy/dbm/` by hand; `dbm` regenerates them and drift breaks `dbm doctor`.
- Do not open new public ports. A new public service goes through Traefik on 443 with its own hostname.
- Do not use `*.web.<domain>` for anything but public buckets.
- After pulling the repo, `npm run build` so the global `dbm` matches the code.

## 11. Working out a request that is not in the skill

Ask these, in order, and write the answers down before acting.

1. **Is it a project database, bucket or auth for a Next.js app?** Use `/dbmanager`. Done.
2. **Does it need Postgres?** Use `dbm create` (and `dbm import <slug> --from <url>` to bring data from any Postgres, not only Supabase; storage flags are optional; it rejects the transaction-pooler port 6543). The import report lists extensions the source used that the target lacks; projects get `pgcrypto` and `uuid-ossp` by default (`dbm create --extensions a,b` adds more). Never run a second, unmanaged Postgres.
3. **Does it need something dbm does not manage (Redis, a queue, an API server, a worker, a cron)?** It runs as a Dokploy service on `dokploy-network`: a Dokploy database (Redis, MongoDB, MySQL) or an application (from a Git repo, a Dockerfile or a compose file). Dokploy attaches its services to `dokploy-network` by default. Keep databases internal (no published port), set a memory limit on every such service (Dokploy, service, Advanced, Resources), and tell the operator it is outside dbm's backups.
4. **Does it need to be reachable from the internet?** Through Traefik only: a new A record and a Dokploy domain on 443. No other ports.
5. **Does it run code on the VPS?** That changes the risk profile: an app container shares the internal network with every project database. Prefer Vercel for app code. If it must run here (a demo), keep it temporary, give it only its own project's credentials, and remove it when done.
6. **Will it fit?** Check memory and disk (section 9): `ssh root@<sshHost> 'free -m; df -h /'`.
7. **How is it recovered?** If the answer is "it is not", say so to the operator before building it.

Example: reviving a backend that ran on Railway with Postgres and Redis, for a demo. Postgres becomes a dbm project (`dbm create` + `dbm import --from <railway public URL>`); Redis becomes a Dokploy Redis service with no public port, treated as a cache; the backend becomes a Dokploy application with its own hostname; the frontend stays on Vercel. The app connects to Postgres with the URL from `dbm env`. Inside the VPS that URL goes out to the public IP and back in; if the provider does not allow that, connect to host `dbm-pgbouncer`, port 6432, with the same credentials. TLS still verifies the certificate for `db.<domain>`, so the client must send that server name: postgres.js and node-postgres take `ssl: { servername: 'db.<domain>' }`; for drivers without such an option, add a host alias `db.<domain>` pointing at `dbm-pgbouncer` in the service's Dokploy settings instead.
